# Apollo.RGA Access Bridge — единая подписка и серверный допуск OlcRTC

Дата: 2026-09-27. Статус: владелец подтвердил отдельный Apollo.RGA Access Bridge и одну Remnawave-подписку; детали серверного допуска, квоты и restricted-network control остаются предметом проверки. Не разрешает production-развёртывание или показ OlcRTC обычным подписчикам.

## Задача и решение

OlcRTC — обязательный будущий транспорт внутри того же Apollo.RGA, а не отдельное приложение, учётная запись или ссылка. Android и Windows используют одинаковую политику подписки; iOS сможет стать следующим потребителем. Для этого нужен небольшой отдельный серверный **Access Bridge**. Он читает текущую Remnawave-подписку, выдаёт клиенту понятное состояние и служит обязательной точкой допуска для OlcRTC-сервера. Клиентское «срок истёк» полезно для UI, но не является механизмом отключения: изменённый или спящий клиент нельзя считать доверенным счётчиком.

Порядок клиентской реализации, утверждённый владельцем: **Android → Windows → Android TV → macOS**. Windows начинается после полной реализации Android; Android TV — после Android и Windows; macOS — после всех трёх. Общий DTO и серверный допуск не заменяют отдельные платформенные проверки VPN/TUN, сна, ввода, UI и установки. iOS не включён в этот порядок и требует отдельного решения.

Размещение — изолированный модуль Apollo.RGA. Apollo.GAP/AWG не являются владельцем этого runtime, квоты или допуска и не входят в путь подключения. Возможное упразднение GAP — отдельная миграция, а не действие этого этапа. Remnawave остаётся источником статуса, срока, исходного лимита и обычного Xray-usage. Bridge владеет только связью подписки с установками, отдельным флагом OlcRTC, допусками и внешними байтами OlcRTC. Platform-право на модуль, если оно применяется к этой подписке, может дополнительно отказать, но не заменяет Remnawave-статус и само по себе не выдаёт VPN-доступ.

## Разделение полномочий

| Компонент | Делает | Не делает |
| --- | --- | --- |
| Remnawave | Подтверждает пользователя, статус, срок, исходный лимит, цикл сброса, Xray-usage и HWID-политику | Не считается учётчиком внешних OlcRTC-байтов без подтверждённого API/интеграции |
| Access Bridge | Сверяет Remnawave, хранит `olcrtcEnabled` отдельно для каждой подписки, выдаёт/отзывает короткие допуски, ведёт durable OlcRTC-meter и общий бюджет | Не выпускает второй пользовательский аккаунт и не отдаёт административный токен клиенту |
| OlcRTC-сервер | Проверяет допуск при входе и периодически, считает двусторонние egress-байты, разрывает сессию при отказе/лимите | Не доверяет флагу, времени и счётчику Android/Windows |
| Apollo.RGA клиент | По старой ссылке связывает установку, получает redacted policy snapshot, показывает режим/срок/остаток и прекращает соединение при отказе | Не обращается к административному API Remnawave и не решает самостоятельно, что квота ещё есть |

Канонический субъект на подтверждённой Remnawave v3 — `(panelInstance, numericUserId)`. `shortUuid` и полный subscription URL — сменяемый bearer только для первоначального связывания и обновления; их нельзя использовать как постоянный ключ ledger или передавать OlcRTC-ноде. Отдельная установка имеет свой ключ и непрозрачный installation ID. Первое связывание не создаёт новую пользовательскую учётную запись, но не должно обходить действующий лимит устройств/HWID; семантику связи этих двух проверок нужно подтвердить на установленной версии панели.

## Контракт синхронизации и допуска

1. Клиент передаёт уже имеющуюся ссылку Access Bridge только по HTTPS и только при первоначальном связывании/обновлении права; URL исключён из access-log, crash-log и аналитики. Bridge разрешает её через серверный Remnawave adapter и сохраняет только канонический субъект и защищённую привязку. Admin API token хранится только на сервере с минимально доступными правами.
2. `PolicySnapshotV1` для Android/Windows содержит: непрозрачный subject, revision, serverTime, status, expiresAt, cycleEnd, totalLimitBytes, confirmedUsedBytes, remainingBytes, `olcrtcEnabled`, `ordinaryAllowed`, `alternateAllowed`, причину отказа и `refreshAfter`. Это состояние для интерфейса и локального fail-closed поведения, не пропуск на сервер. При ошибке обновления клиент показывает «данные устарели», не продлевает срок локальными часами и не выдумывает оставшуюся квоту.
3. `AlternateGrantV1` выдаётся только после свежей проверки Remnawave, per-subscription флага, привязки установки, доступной комнаты той же страны и свободного зарезервированного бюджета. Он привязан к installation, room, country, audience `OLCRTC`, policy revision, session ID, `jti`, server expiry и небольшому byte lease. Комната принимает его однократно, сверяет с Bridge и продолжает проверять доступ при работе; повтор, чужая комната/установка, отзыв или истечение — отказ.
4. Отключение `olcrtcEnabled` запрещает новые OlcRTC-сессии и отзывает действующие, не выключая обычный Xray. Истечение, исчерпание **общей** квоты или авторитетный Remnawave-отзыв запрещает оба режима. Webhook — только сигнал для быстрой повторной сверки: доставка, порядок и уникальность не считаются гарантированными; есть периодический reconciliation и монотонная policy revision.
5. Для ограниченного LTE клиент может заранее получить непрозрачный bootstrap, но сервер всегда повторно проверяет актуальное право при join. Не рассчитывать на прямой HTTPS к Bridge в сети, где обычные входы не достигаются. Холодный старт без доступного bootstrap/канала остаётся `AlternateUnavailable`, а не открытым доступом.

## Обновление подписки при ограниченной сети и обязательный серверный отзыв

Существующий Android-клиент уже обновляет **ту же Remnawave-ссылку** через SOCKS работающего туннеля: при подключении, вручную и по расписанию (`HomeScreenModel.kt`, `AndroidVpnManager.kt`, `LocationsHttpClient.android.kt`). Если OlcRTC-туннель действительно поднят в сети с белым списком, этот путь должен использовать его локальный SOCKS и получать обычную конфигурацию без второй подписки. Для нового `PolicySnapshotV1` нужен отдельный короткий refresh после подключения и при смене состояния; пользовательская настройка частоты обновления списка хостов не может отключать проверку допуска. Физический тест на A063 с ограниченным LTE остаётся обязательным: наличие кода SOCKS не доказывает доступность Remnawave URL через конкретную OlcRTC-комнату.

Сегодня обычный HTTP 403 или ошибка сети при обновлении сохраняют последний рабочий список хостов; только явный HWID-отказ помечает устройство как запрещённое. Локально известные expiry/limit продолжают блокировать подключение, но старый список хостов сам по себе не доказывает действующую подписку. После истечения `getActiveLocation()` уже не даёт поднять OlcRTC для нового refresh, поэтому status-only control path ниже — отдельное обязательное требование, а не свойство нынешнего updater.

Обновление на клиенте **не** является отзывом права. Сервер проверяет Remnawave и общий бюджет при admission, а затем выдаёт только ограниченный по времени и байтам lease. OlcRTC-нода повторно сверяет его через Bridge, считает байты во время передачи и сама закрывает активную сессию при expiry, отзыве, исчерпании резервации или неуспешном продлении lease. Узел обязан иметь локальный жёсткий дедлайн не позже срока подписки и дедлайна lease: если push от Bridge или клиентский refresh не дошёл, подключение не остаётся вечным. При недоступности Bridge/панели новые OlcRTC-сессии не выдаются, а активные завершаются к дедлайну lease; обычный Xray не выключается из-за сбоя Bridge. Срок lease и максимально допустимую задержку разрыва задаём только после нагрузочного и физического теста, но результат обязан иметь измеренную конечную границу.

Закрытие по сроку может лишить клиента обычного прокси для получения сведений о продлении в той же ограниченной сети. До выпуска нужен минимальный **status-only** control path через проверенный OlcRTC carrier: привязанная установка может запросить только собственные `status`/`revision` и, после подтверждённого продления, новый admission; это не произвольный SOCKS/HTTP proxy и не доступ к интернету при истёкшей подписке. Если такой канал на pinned fork невозможно доказать, честный результат — `AlternateUnavailable` до появления обычной сети, а не бессрочный OlcRTC-доступ. Subscription URL не попадает в OlcRTC-ноду или её логи; Bridge принимает только заранее разрешённый panel origin при первоначальной привязке, затем использует device-bound opaque credential.

Текущий pinned Ghostlane fork требует доработки, а не одной настройки: handshake допускает внешний `AuthHook`, но стандартный server CLI принимает PSK-пира без subscription claims; Android binding не передаёт grant, а meter подтверждает байты только при закрытии потока. При этом CLI сегодня выводит `claims` в лог, поэтому перед передачей любого grant требуется удалить/редактировать такой вывод. Серверный `closeSession` пока внутренний; не подтверждён внешний API для принудительного завершения. Control protocol содержит ping/pong/close, но не policy RPC, а обычный exit не ограничен одним policy endpoint — **status-only путь сейчас отсутствует**. Поэтому нельзя включать режим подписчикам, пока не реализованы и не проверены server admission, потоковый meter, активный close, отзыв при client-killed/screen-off и ограниченный control path. Локальный Android watchdog по сохранённым данным полезен для UX, но не является доказательством отзыва на сервере.

## Общая квота: обязательное доказательство

Сумма за текущий цикл — подтверждённые Xray-байты Remnawave плюс учтённые OlcRTC-байты и активные резервации. OlcRTC-сервер отправляет монотонные cumulative snapshots по обоим направлениям; запись идемпотентна по `(sessionId, sequence)` и переживает повтор, обрыв и рестарт. Нельзя основывать лимит на счётчике телефона, webhook о пороге, `OnTraffic` только при закрытии потока или отдельном несвязанном OlcRTC-лимите. Резервирование небольшими lease-блоками ограничивает параллельный перерасход.

Открытый технический вопрос — **Xray-side enforcement**. Публичная документация Remnawave подтверждает чтение `userTraffic`, изменение пользователя/лимита и disable, но не подтверждает атомарного внесения внешних OlcRTC-байтов в её счётчик. До реализации нужно на изолированной подписке проверить установленную production-версию, задержку доставки Xray-usage, действие изменения лимита/статуса на **активные** сессии, цикл reset/renewal и возможный node-side механизм. Если допустим только периодический sync, описать измеренную верхнюю границу перерасхода и явно согласовать её; не называть такой результат строгим общим лимитом. При недоступном ledger/неизвестном статусе новый OlcRTC grant не выдаётся, активный истекает не позднее короткого lease; обычная подписка не отзывается из-за одного сбоя Bridge.

## Безопасное внедрение

- Отдельный read-only Remnawave adapter и контрактные фикстуры без реальных URL/ключей. На этом шаге `olcrtcEnabled=false` для всех.
- Foundation parser на клиенте пока не получает сетевой DTO и не показывает общий остаток: окончательный `PolicySnapshotV1` обязан добавить `cycleEnd` и подтверждённые OlcRTC-байты/резервации. Чтение одного Remnawave `userTraffic` не является расчётом общей квоты.
- Durable ledger/admission и изолированный OlcRTC-сервер с отрицательными тестами: параллельные устройства и Xray/OlcRTC, duplicate meter, reset/renewal, revoked/expired grant, outage, активный disconnect, проверка ограниченного LTE bootstrap. Не проводить отрицательные quota/HWID-тесты на действующих пользовательских подписках.
- Клиентский синхронизатор `PolicySnapshotV1` для Android и Windows с одной Remnawave-ссылкой, редактируемыми пользовательскими объяснениями и скрытым режимом до допуска. В обычном release OlcRTC runtime и URI остаются недоступны, пока не доказаны native provenance, маршруты, полный TUN и общий серверный enforcement из утверждённой спецификации ограниченной сети.
- Приёмочный тест отзыва: запустить OlcRTC на тестовой подписке, затем остановить/заморозить клиент и выключить автообновление. Истечение срока, ручное выключение OlcRTC, превышение общего лимита и недоступность Bridge должны в измеренный срок разорвать **серверную** сессию. После истечения status-only канал может сообщить о последующем продлении, но не пропустить пользовательский трафик до нового admission.
- Только после физической проверки и отдельного решения владельца включать режим подписчикам. Rollback: отозвать выдачу grants, остановить OlcRTC-сессии; обычные хосты и исходная ссылка продолжают работать.

## Проверенные источники и неизвестное

- [Remnawave API v3.4.4](https://docs.rw/api/) документирует пользователя, `shortUuid`, статус/срок/лимит/`userTraffic` и операции управления. Текущая установленная production-версия и доступность отдельных методов здесь не проверены.
- [Remnawave webhooks](https://docs.rw/features/webhooks/) документируют HMAC и события; строгая последовательность и exactly-once не документированы.
- Исходный [olcRTC upstream](https://github.com/openlibrecommunity/olcrtc) архивирован/EoL, но клиент закрепляет поддерживаемый [Ghostlane fork](https://github.com/ghostlane-project/olcrtc) в `scripts/cores-pins.sh`; это отдельный кандидат на проверку source/binary provenance и редактирования логов перед release. [snolc](https://github.com/owenewans/snolc) — возможный преемник, но Android/Telemost/квотная пригодность для нашего сценария ещё не доказана.
- Производственный endpoint/wire-формат Bridge, версия установленной панели, точный источник Xray-дельт, предел отключения активных Xray-сессий и доступность bootstrap из ограниченной сети — **unknown**, не скрытые предположения.
