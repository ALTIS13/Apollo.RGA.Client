# Apollo.RGA Android — исходники и выпускной барьер

Дата: 2026-09-26. Статус: кандидат в отдельной локальной ветке `codex/apollo-rga-client-mvp`; **не выпуск, не развёртывание и не изменение Remnawave**. `origin` этого checkout указывает на upstream Ghostlane, поэтому ветка туда не отправлена.

## Что готово в исходниках

- Используется буквальная HTTPS-ссылка существующей подписки. Строгий XRAY_JSON-декодер принимает набор целиком или отклоняет его, сохраняя DNS, routing, outbounds, Reality/XHTTP и Hysteria 2. Подмена точного профиля локальным `Bypass Russia` не считается успешным импортом XRAY_JSON.
- Android-кандидат Xray 26.9.9 запускает проверенный профиль через существующий VPN service; неизвестные поля или небезопасное переписывание дополнительного HTTP-inbound отклоняются. Исходный профиль хранится без перестройки его маршрутов. Это **не** доказательство живого трафика.
- Обычный интерфейс Apollo.RGA показывает страну выхода первым флагом, протокол, выбранный хост, срок/лимит и состояние подключения. OlcRTC скрыт и запрещён в обычном выпуске до доказанного общего срока и учёта трафика.
- Новое версионированное согласие на Android VPN проверяется как в интерфейсе, так и перед запуском service через приложение, Quick Settings или always-on. Отключение VPN не блокируется. Первый импорт сохраняет локальные настройки, маршрутизацию, согласие и отметку вводного экрана.
- При неоднозначном сопоставлении изменившегося XRAY_JSON-профиля обновление не подменяет выбранный хост. Но более ранний известный срок и более строгая квота из достоверно разобранного ответа сохраняются для прежней подписки, в том числе до наступления нового срока. Последующий более мягкий ответ в этой неоднозначной ветке не ослабляет ограничение.
- QR и вставка ссылки внутри приложения сохраняются. Внешние Android Intent отклоняются во всех вариантах сборки до проверенной owned HTTPS-ссылки и экрана подтверждения; это исключает автоматический импорт из другого приложения. Разбор будущей HTTPS-ссылки сделан отдельно, но не подключён. Ошибки импорта не выводят исходный текст исключения, который мог содержать адрес или токен подписки.

## Проверено

- JVM: 757/757 после исправления неоднозначного обновления. Адресные Android host-тесты согласия service, первого импорта и запрета внешних Intent прошли; Android debug/release Kotlin и Android common код компилируются. Тесты демонстрируют отказ по исчерпанному лимиту/истёкшему сроку и своевременное применение будущего более раннего срока без подмены профиля, выбора, порядка и времени последнего обновления.
- Текущий read-only снимок Remnawave: производный XRAY_JSON-ответ содержит восемь профилей, 8/8 прошли точный codec и Android adapter без потери DNS/routing/outbounds. **Буквальная** пользовательская ссылка при `ApolloRGA/0.1` пока возвращает JSON-объект, а не XRAY_JSON-массив. Никакое Response Rule не менялось.
- На отдельном API 36 x86_64 эмуляторе приложение открылось без прежнего SVG-сбоя; проверены вводный экран, главный экран, длинное синтетическое имя при масштабе шрифта 1.3, экран согласия и последовательность «чистая установка → первый синтетический импорт → перезапуск» без повторного onboarding. Эта визуальная проверка прошла до закрытия debug-внешнего импорта; последующее изменение лишь отклонило внешние Intent, не меняя хранение/внутренний импорт. Тестовый хост **не подключался**. Эмулятор остановлен, A063 пользователя не использовался.
- Собранный для визуальной проверки debug APK исключал сборку отсутствующего локального OlcRTC AAR и проверку неразмещённых x86/armeabi sing-box cores. Он **не годится для распространения или проверки реального VPN**. Точное Android arm64 ядро Xray ранее прошло проверку запуска и синтетических VLESS/Hy2 схем, но не живой сетевой маршрут.
- Последний широкий Android host-запуск был красным: 33/621 против прежних 23/538. Добавившиеся UI-тесты упираются в неподготовленный host Compose/Android runtime (`Build.FINGERPRINT` и `Resources.getSystem`); после адресных исправлений этот набор не повторялся без конкретной новой причины. Его результат не объявляется ни успешной Android-приёмкой, ни доказанной продуктовой регрессией.

## До пользовательского выпуска обязательно

1. Снять приватный prestate действующего ответа подписки и INCY/Happ. Только после отдельного решения о production изменить узкое Remnawave Response Rule для **той же буквальной ссылки** и только собственного User-Agent; затем повторно проверить XRAY_JSON, HWID/допуск, срок/лимит и неизменность INCY/Happ. Если точный ответ по той же ссылке недостижим, выпуск заблокирован.
2. Собрать подписанную сборку с проверенными исполняемыми cores для выпускаемых ABI и требуемым OlcRTC build input либо доказанно исключить его из обычного варианта. Локальная визуальная APK не заменяет эту проверку.
3. После предупреждения пользователя и возвращения A063: на физическом Android проверить реальный VLESS/XHTTP/Reality и Hy2, RU DIRECT с адреса устройства, иностранный egress выбранной страны, DNS, IPv4/IPv6, смену Wi-Fi/LTE, сон/возобновление, лимит/срок и отсутствие URL/ключей в логах. Не использовать синтетическую проверку ядра вместо этого.
4. Для кнопки «Установить и добавить» выбрать принадлежащий Apollo.RGA HTTPS host/path, настроить verified App Link и `assetlinks.json` для окончательного package/signing lineage, добавить подтверждение импорта в приложении и доказать открытие на подписанном Android. До этого выпуск ограничен QR/вставкой; токен не размещать в HTTP path/query и не логировать.
5. Лишь после этих проверок обновлять production-страницу подписки, сохранив INCY/Happ как альтернативы на переходный период. iOS — отдельный этап.

Ни Remnawave, ни DNS, ни узлы, ни страница подписки, ни другие проекты этой работой не изменялись. Приватные ссылки, ключи и payload в этот документ не включены.
